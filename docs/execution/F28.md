# F28 — Hardening OTA, CSP y checkpoint de artefactos

Fecha: 2026-09-15 (`America/Lima`)

## Objetivo

Cerrar el bloque de actualización móvil opcional sin convertirlo en requisito del checkout, eliminar declaraciones de tracking no usadas y dejar artefactos Android reproducibles e identificables.

## Cambios

- `src/lib/liveUpdate.ts`: validación estricta de origen/ruta, bundle ID, ZIP, checksum, firma y `content-type`; timeout de 10 s con `AbortController`; cualquier error mantiene abierta la aplicación empaquetada.
- `scripts/prepare-mobile-live-update.mjs`: base HTTPS exacta de Suya y bundle ID seguro; la clave privada no se imprime.
- `public/_headers`: se elimina GA/GTM de CSP, se autoriza solo el origen del manifest OTA y se fijan `Content-Type`/cache para `latest.json` y los ZIP.
- `tests/mobile-live-update.test.ts` y `tests/security-hardening.test.ts`: regresión focal OTA/CSP.

## Evidencia

- Focal OTA/CSP: **7/7**.
- Suite Vitest: **68 archivos / 301 pruebas**.
- `npm run typecheck`: pasa.
- `npm run lint`: pasa.
- `npm run build`: pasa.
- `npm run verify:apps`: pasa; bundles customer, rider y backoffice aislados.
- `npm run security:secrets`: pasa; 909 archivos sin patrones de secreto.
- `npm audit --omit=dev --audit-level=high`: 0 vulnerabilidades.
- `verify:production`: rechaza correctamente la ausencia de configuración productiva y no realiza despliegue.
- Endpoint consultado: HTTP 200 con HTML, no manifest JSON; el cliente lo rechaza y no se habilitó OTA.
- APKs debug: ZIP íntegro, un firmante y APK Signature Scheme v2 válido; versión `1.4`, código `5`.
- La preparación del emulador temporal no avanzó: `sdkmanager` no pudo descargar los catálogos remotos y el SDK aislado no contiene emulator/system image. No se modificó el sistema ni se falsificó smoke nativo.

## Bloqueos y siguiente comando

El flujo oficial `supabase db lint/test` necesita un daemon/puerto local accesible. Las pruebas SQL independientes no sustituyen ese gate. También faltan dispositivo, firma release, endpoint vial privado y autorización/configuración de pagos. El primer comando tras resolver el runtime SQL es:

```sh
npm run db:start && npm run db:lint && npm run db:test
```

Después repetir la suite global, `npm run build:mobile:roles`, smoke nativo y la matriz de pagos sin usar datos reales.
